## 3. Decisions already taken — do not relitigate these

Each of these was decided deliberately. If you disagree, change it knowingly,
but do not "fix" it as if it were an oversight.

**The taxonomy is the HSC/NCTB syllabus.** 51 chapters, 183 topics, generated by
`Backend/tree_data/build_syllabus_config.py`. Edit that script and re-run it —
never hand-edit `ontology_config.json`.

**`topic_aliases` is now a no-op for the rebuild.** Every skill in `tuples.json`
carries a syllabus topic code directly. The alias map still exists for the
legacy ontology. Do not reintroduce alias-based topic assignment: it was a
code-to-code map, and the reason 54 topics sat empty while their siblings held
154 skills.

**Cross-subject overlap is linked, not merged.** HSC teaches some skills twice —
Higher Math 2nd Paper Dynamics repeats Physics 1st Paper kinematics almost
verbatim. Merging would empty `MAT2_PLANE_MOTION` and `MAT2_PROJECTILE`. Both
nodes are kept, marked `crossSubjectEquivalent`, and joined by a prerequisite
edge pointing at whichever subject teaches it first. This is why the validator
still reports **4 exact duplicate descriptions** — they are intentional.

**Granularity is accepted at median 7 skills/topic.** Four Chemistry topics
exceed 40 (`CHE1_REDOX` 48, `CHE1_PERIODIC_TRENDS` 47, `CHE1_ACID_BASE` 46,
`CHE1_COVALENT_BOND` 44). They are deliberately **not** split, because the NCTB
syllabus does not subdivide them. Splitting is a taxonomy decision, not an
extraction one.

**51 skills are authored, not extracted.** They carry `"authored": true` and no
corpus item teaches them — assumed knowledge like "solve a linear equation",
"evaluate a logarithm", "balance a chemical equation". Three topics
(`MAT2_EXPONENTIAL_EQ`, `PHY1_ERRORS`, `PHY1_SOLID_BONDING`) consist **entirely**
of authored skills. Expect RAG retrieval to be weak for those; see §5.

## 4. Two heuristics that over-flagged — a warning about the next one

This project has now had **two** mechanical quality checks report a large defect
count that hand-review mostly dissolved. Budget for this pattern.

1. **Multi-action regex** (recorded in `quality_audit.md`): flagged 173 skills,
   >50% false positives. Replaced with a defensible criterion giving 47.
2. **Bloom inversions** (`_validate_ontology.py` check E2): flagged **147** edges
   as errors. Hand-review found **3** genuinely reversed. The check was wrong,
   not the data:

   ```
   MAT_MATRIX16 (Remember: a determinant with two equal rows is zero)
       requires MAT_MATRIX13 (Apply: evaluate a 3x3 determinant)
   ```

   which is the correct order. **Bloom tier measures cognitive demand, not
   teaching sequence.** A low-tier *fact about* an operation is routinely learned
   after the operation. E2 is now WARN-level and kept only as a review list.

Similarly, `_propose_fragment_links.py` was ~40% usable on its first scoring
heuristic (it proposed lateral links between peers, and one pair in both
directions, which would have closed a cycle). **Never apply its output
unreviewed.**

The lesson: on this ontology, run the heuristic, then read every hit.

## 5. What to do next — generating questions

### 5.1 The blocker you must fix first

`data-gen/rag/config.py:10` hardcodes:

```python
ONTOLOGY_SOURCE_DIR = BKTBACK_DIR / "Backend" / "tree_data" / "ontology_source"
```

That is the **legacy 430-skill** ontology. Generating today would produce
430 × 6 = 2,580 tuples against the old skill set instead of 1,688 × 6 = **10,128**
against the new one, and you would pay for all of it.

Note the subtlety: adoption (`build_from_ontology.py --out-dir Backend/tree_data`)
writes the *compiled* catalog and does **not** touch `ontology_source/`. So
adopting the rebuild without also repointing the generator makes the Backend
serve 1,688 skills while the generator still reads 430 — the exact drift
`data-gen/rag/README.md` claims is impossible.

Point it at `Ontology/full_corpus_rebuild`. Format is compatible: same six
required fields, same `prereqs.json` shape. The rebuild's extra keys
(`authored`, `splitFrom`, `crossSubjectEquivalent`) pass through `dict(tup)`
harmlessly.

### 5.2 Things already handled — do not "fix" them

- **Bloom coverage.** 36 topics hold only one Bloom level, but
  `question_gen_common.py::expand_bloom_levels` already emits one tuple per
  skill × all 6 levels, precisely because the engine tests one level above a
  learner's band. Nothing to do.
- **Corpus grounding.** Skills carry no `sourceItemIds`, and they do not need to:
  the RAG retriever finds similar corpus units per tuple at generation time.
  (Traceability is ~91.5% recoverable by exact description match against
  `candidates/*.json` if you ever want it for auditing.)

### 5.3 Expect these to generate badly

- The **51 authored skills**, especially the three all-authored topics — no
  corpus question supports them, so retrieval returns weak or unrelated context.
- The **4 exact duplicate descriptions** from the cross-subject pairs will
  generate near-identical questions in two subjects. That is expected.

### 5.4 Scale

1,688 skills × 6 Bloom levels = **10,128 tuples**. `HANDOFF3.md` documents a
cost blow-out on this project — read it before starting a long run, and use
`check_progress.py`.

## 6. What is genuinely unfinished

Nothing structural. Everything below needs a human with the subject, not a tool.

1. **32 near-orphan fragments.** The 35 rejected proposals from
   `_propose_fragment_links.py`. Rerun it to see them. Rejected because the
   proposed edge was backwards, joined unrelated same-chapter skills, or linked
   two peers needing a common parent. **A wrong prerequisite edge propagates
   through the ancestor pull-up and silently corrupts mastery estimates — worse
   than a missing one.** Do not guess.
2. **Domain review of 352 hand-authored Chemistry backfill edges** from the
   earlier sparsity fix, especially in organic topics. The graph is depth 9 now,
   so a wrong edge travels far.
3. **Domain review of the 51 authored skills.**
4. **29 higher-tier skills with no prerequisite** (`_validate_ontology.py` E5).
   Each was examined; no candidate parent was clearly right.
5. **`che1_ch05_applied`** holds only 5 skills moved in from descriptive
   chemistry — the thinnest real chapter.

## 8. Traps

- **Never name a generated viewer `skill_ontology_dag.html`**, and never put one
  in a directory passed as `--source-dir`. `build_from_ontology.py::load_source()`
  treats that exact filename as authoritative input and will silently use it
  instead of `tuples.json`. `build_dag_viewer.py` refuses to write that name.
- **The legacy ontology is read-only reference**: `Ontology/{tuples,prereqs}.json`,
  `Ontology/skill_ontology_dag.html`, and everything under
  `Backend/tree_data/ontology_source/`. Do not edit them.
- **`Backend/.env` holds a Supabase service key.** Gitignored, secret, full DB
  access. Never invent, guess or stub it. A missing `.env` causing `KeyError` is
  expected behaviour, not a bug.
- **`_consolidate_incremental.py` had an id-minting bug** that fabricated a DAG
  cycle (regex could not match topic codes containing digits). Fixed, plus a
  duplicate-id guard that refuses to write. Documented in STATUS.md. If you
  write another consolidator, do not repeat the `^([A-Za-z_]+?)(\d+)$` pattern.
- **Windows console encoding**: prefix Python invocations with
  `PYTHONIOENCODING=utf-8` or Bangla text raises `UnicodeEncodeError` on cp1252.
- **Every editorial script takes `--dry-run`** and refuses to write on a cycle,
  an unknown skillId or an id collision. Use it.
- **Backups of every pass** are in `Ontology/full_corpus_rebuild/_prefix_backup/`:
  `*.pre_retag`, `*.pre_foundations`, `*.pre_split`, `*.pre_merge`,
  `*.pre_valfix`, `*.pre_fraglinks`. Restore from these if a judgement is
  disputed.
